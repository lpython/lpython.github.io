webgpu-waveform · LOD pyramid · range-query exactness

Conservative, Not Exact

A min/max pyramid can be sloppy at its edges and still look right. A mean/σ pyramid cannot. Eight plates on why that asymmetry exists, what it costs, and what an exact query has to do instead — the one part of webgpu-waveform's design that does not transfer to gl-waveform.

Companion to the library comparison. Figures are computed at load from a real signal, not drawn by hand.

teaching figures: column 40 samples bin 16 ratio 1 : 2.5 real ratio is 1 : 64 — stated alongside where it matters
PLATE 01

A pyramid is a grid, and the grid does not move

Each level summarises fixed, aligned blocks of the level below. Bin b at a level with bin size S owns exactly samples [b·S, (b+1)·S) — always, regardless of what you later ask for.

// buildMinMaxPyramid, ratio 64
level 1  bin =      64 samples
level 2  bin =   4 096
level 3  bin = 262 144

That fixity is what makes the pyramid cheap: no bookkeeping, pure index arithmetic, and each level is built once in a single linear sweep of the one below.

It is also the entire problem. A pixel column is defined by the viewport — by scale and offset, which change every time the user pans. The column boundaries slide continuously; the bin boundaries never move. They will almost never line up.

Three levels over the same samples. Bin edges are locked to multiples of the bin size at every level.

PLATE 02

A column is not a bin range

The shader converts a sample span into a bin span by division, and division rounds outward on both ends:

let b0 = startSample / binSize;
let b1 = (endSample - 1)
         / binSize;
for (var b = b0 + 1;
     b <= b1; b++) { ... }

So the bins actually read cover [b0·S, (b1+1)·S), which contains the column's true span [s0, s1) and generally exceeds it — by up to S−1 samples on the left and S−1 on the right.

Drag the column. The overhang breathes as it slides, and jumps whenever an edge crosses a bin boundary. Nothing is wrong with the code — this is exactly what integer division is supposed to do.

column [s0, s1)bins readoverhang

Teaching ratio 1:2.5, so the overhang is large enough to see. At the real 1:64 it is at most ~3% of a column — small, but never zero, and never stationary.

PLATE 03

For min/max, the overhang can only add

min and max are idempotent and monotone under union. Adding samples to a set can lower the min and raise the max; it can never do the reverse.

A ⊆ B  ⟹  max(A) ≤ max(B)
       and  min(A) ≥ min(B)

The bins read are a superset of the column. So the envelope you get is a superset of the true envelope: it may be too tall, never too short. A peak is never hidden, only occasionally borrowed from a neighbour.

This is what the source means by "conservative — the envelope only ever grows, never clips." For an audio peak display that is precisely the safe direction to be wrong in. You would rather see a transient one pixel early than not see it.

Same column, same overhang. The computed envelope brackets the true one on both sides. The shaded difference is the overhang's only possible contribution.

PLATE 04

The proof is in the sign

Slide the column across 400 offsets and plot the error against the true value. The two statistics behave categorically differently, and you can read it straight off the zero line.

Envelope error is one-sided. Over 400 offsets the sign of max_computed − max_true takes only the values {0, +1}. It is never negative. Not "rarely" — never, as a consequence of the subset relation in Plate 03.
Mean error is two-sided. Over the same 400 offsets: 176 negative, 184 positive, 40 exact. It oscillates around the truth with a period equal to the bin size, because which extra samples get a vote depends on where the bin grid happens to fall.

A one-sided error is a bias — a known, bounded, directional distortion you can reason about and accept. A two-sided error is noise. There is no argument of the form "it only ever grows" available for the mean, because it does not only ever grow.

Error against column offset, computed at load. Top: envelope, entirely on one side of zero. Bottom: mean, crossing zero on almost every bin boundary. Same signal, same pyramid, same query.

PLATE 05

Two-sided error is not error. It is jitter.

A static wrong number is tolerable. The problem is that the error is a function of offset — and offset is what changes when the user pans.

So as the waveform scrolls, every column's mean walks up and down its own little sawtooth, with a period of one bin. The rendered line shimmers against a signal that has not changed. Worse, adjacent columns are at different phases of that sawtooth, so the shimmer is spatially incoherent — it reads as crawling noise rather than a clean sub-pixel slide.

The envelope shimmers too, at the same period. But it only ever grows, so the visual effect is a boundary that breathes outward slightly — far less objectionable than a centreline that wanders.

This is the same class of defect as the pxStep = 0.5 column decimation in gl-waveform: correct-looking when static, wrong in motion, and invisible to any test that renders one frame.

One column's computed mean as the view pans one bin at a time. The true mean moves smoothly; the pyramid estimate staircases around it.

PLATE 06

σ is worse than the mean

The overhang does not just shift the centre — it admits samples the column never contained, and variance punishes outliers quadratically.

A single loud sample just outside the column raises the computed σ by an amount proportional to its squared distance from the mean. The envelope would have absorbed it harmlessly; the variance amplifies it.

// max |error|, 400 offsets
          mean     sdev
 1:2.5   0.302   0.176
 1:64    0.0096  0.0042

At the realistic 1:64 ratio the numbers look small — about 1% — but they are 1% of a quantity that is itself driving opacity in the fragment shader, and they move with the offset.

Note the realistic envelope error at that ratio: exactly zero across all 400 offsets. The column is wide enough that it already contains its own local extremes, so the overhang adds nothing. The mean's error at the same ratio is not zero. The asymmetry does not shrink away with a better ratio; it is structural.

One outlier sample in the overhang. The envelope stretches to include it and stops. σ registers its squared distance.

PLATE 07

What exactness costs: the staircase

To get an exact answer for an arbitrary range you cannot use one level. You decompose the range across several levels — coarse nodes in the middle, progressively finer ones toward each edge — so the union is exactly [lo, hi) with no overhang at all.

var l = lo + N;
var r = hi + N;
while (l < r) {
  if ((l & 1u) == 1u) {
    res = merge(res, t[l]);
    l++;
  }
  if ((r & 1u) == 1u) {
    r--;
    res = merge(res, t[r]);
  }
  l >>= 1u; r >>= 1u;
}

That is the standard iterative segment-tree query: about 2·log₂N nodes, climbing one level per iteration and picking up at most two nodes on the way. For a million samples, roughly 40 merges.

The merge must also be exact, which for mean/σ means Chan's parallel formula rather than summing — so the pyramid stores (n, mean, M2), not (sum, sum²). That choice is what removes the catastrophic cancellation as well. Two problems, one structure.

An arbitrary range decomposed. Node widths double toward the middle and halve toward the edges; their union is exactly the requested span, computed and verified at load.

PLATE 08

The two queries, and the premise underneath

Side by side, the difference is not really cost — both are bounded and both are cheap. It is whether the answer is allowed to be approximate.

Both are bounded loops. Only one is exact. Note that the bounded scan is cheaper in the common case and the segment tree is cheaper in the worst case.

Appending K samples dirties a contiguous node range at every level — the update is a widening path, not a rebuild. webgpu-waveform does not implement this: it builds the whole pyramid on the CPU in the constructor and treats the data as immutable thereafter.

Edges of the reading

the premise

Immutability is load-bearing

colMinMax is memoised on (scale, offset, width) and the compute pass is skipped when none changed. That is only sound because channelData cannot change. Add streaming and the memoisation key is wrong, silently — it would serve a stale frame rather than crash.

not a bug

Nothing here is a defect in webgpu-waveform

Conservative is the right call for a min/max audio display, and the source says so plainly in a comment. The finding is only that the property does not survive a change of statistic — which matters if you are porting.

scale

The ratio shrinks the error, not the asymmetry

At 1:64 the mean error falls to ~1% and the envelope error to zero. Tempting to call that good enough — but one is converging to exact and the other is converging to small-and-still-two-sided. Those are different destinations.

alternative

You could also just widen the budget

Scanning raw samples is always exact. Raising COLUMN_LOOP_BUDGET trades loop length for exactness with no new data structure — viable if your zoom range is bounded, useless if it is not.

nuance

Partial edges need level 0

An exact query bottoms out at individual samples, so the tree's leaves must be the raw data. webgpu-waveform deliberately omits level 0 from the pyramid — the fine path reads channelData directly — which an exact query could still do, but the indexing stops being uniform.

testability

All of this is CPU-testable

Every figure here was computed in plain JS against a closed-form signal. The aggregation layer of either library can be tested to machine precision without a GPU, a canvas, or a browser. Neither library does.
